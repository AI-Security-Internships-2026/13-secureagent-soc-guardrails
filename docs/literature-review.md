## Paper Summaries

### Paper 1 — InjecAgent

| Field | Content |
|---|---|
| **Full title** | InjecAgent: Benchmarking Indirect Prompt Injections in Tool-Integrated Large Language Model Agents |
| **Authors** | Zhan, Q., Liang, Z., Ying, Z., Kang, D. |
| **Year** | 2024 |
| **Venue** | Findings of ACL 2024 |
| **URL / DOI** | https://arxiv.org/abs/2403.02691 |
| **Method** | Benchmark of 1,054 test cases evaluating tool-integrated LLM agents against indirect prompt injection embedded in tool outputs (e.g. emails, web content, logs) |
| **Dataset** | Synthetic tool-use scenarios across multiple agent tasks |
| **Key result** | Reinforcing attacker instructions with a "hacking prompt" nearly doubles the attack success rate against ReAct-prompted GPT-4 |
| **Limitation** | Synthetic benchmark; does not cover real-world SOC log formats or domain-specific injection patterns |
| **Relevance** | Directly models the threat in this project's input guardrail layer — malicious instructions hidden inside alert/log data that the SOC agent ingests (maps to RQ3) |

**Notes:**
> Most directly applicable paper for the "Input Guardrail" box in the architecture diagram. Useful as a template for building our own injection benchmark in `experiments/`.

### Paper 2 — SelfCheckGPT

| Field | Content |
|---|---|
| **Full title** | SelfCheckGPT: Zero-Resource Black-Box Hallucination Detection for Generative Large Language Models |
| **Authors** | Manakul, P., Liusie, A., Gales, M. |
| **Year** | 2023 |
| **Venue** | EMNLP 2023 |
| **URL / DOI** | https://arxiv.org/abs/2303.08896 |
| **Method** | Samples multiple stochastic responses to the same prompt and measures consistency between them — sentences that vary a lot across samples are flagged as likely hallucinated, with no external knowledge base required |
| **Dataset** | WikiBio-based passages generated by GPT-3, human-annotated for factuality at the sentence level |
| **Key result** | Sentence-level consistency scoring detects non-factual sentences competitively with methods that require access to the model's token-level output probabilities, despite being fully black-box |
| **Limitation** | Zero-resource means it can't confirm a claim is *true* against a ground truth — only that the model is *inconsistent* about it, which is a weaker (but cheaper) signal than external verification |
| **Relevance** | Direct methodological anchor for the project's planned SelfCheckGPT comparison (Aug 23 milestone) — contrasts with this project's own approach, which verifies against an authoritative external source (NVD/MITRE) rather than checking self-consistency alone |

**Notes:**
> Replaces the earlier "Survey on Hallucination in LLMs" citation — that survey's own most useful content *was* a description of this paper, so citing SelfCheckGPT directly is strictly better: it's the primary source, and it's the actual technique in scope for the cross-method comparison later in the project.

### Paper 3 — TRAM (Threat Report ATT&CK Mapper)

| Field | Content |
|---|---|
| **Full title** | Threat Report ATT&CK Mapper (TRAM) |
| **Authors** | MITRE Engenuity Center for Threat-Informed Defense (with CrowdStrike as a contributing partner on the LLM-based version) |
| **Year** | v1: 2021; LLM-based update: 2023 |
| **Venue** | Open-source project (GitHub, Center for Threat-Informed Defense) |
| **URL / DOI** | https://github.com/mitre-attack/tram ; https://ctid.mitre.org/projects/threat-report-attck-mapper-tram-v1/ |
| **Method** | Trains/fine-tunes ML models (originally classical NLP, later LLM-based) to automatically identify MITRE ATT&CK technique mentions in prose-format cyber threat intelligence reports, with a human-in-the-loop validation UI |
| **Dataset** | Corpus of analyst-annotated threat intelligence reports mapped to ATT&CK techniques |
| **Key result** | Automates a task that is otherwise manual, slow, and inconsistent across analysts — mapping free-text threat reports to structured ATT&CK technique IDs |
| **Limitation** | Extracts/maps technique mentions from *trusted* analyst-authored reports; does not address the adversarial case this project targets — an LLM *fabricating* a technique ID that was never actually present, or citing a real-but-irrelevant one |
| **Relevance** | Closest existing prior art to this project's MITRE ATT&CK grounding checker (Week 9). TRAM solves "find real technique mentions in text"; this project solves the complementary, adversarial problem — "verify a *claimed* technique citation is real, current, and topically grounded" — worth stating explicitly as the point of differentiation |

**Notes:**
> Replaces the earlier "AI-Augmented SOC Survey" citation. This is a much stronger match — it's the one existing system doing ATT&CK-from-text extraction, which is exactly the space this project's own contribution sits in. Frame the comparison as extraction (TRAM) vs. adversarial verification (this project) — that contrast is a good sentence for the paper's related-work gap statement.

### Paper 4 — NeMo Guardrails

| Field | Content |
|---|---|
| **Full title** | NeMo Guardrails: A Toolkit for Controllable and Safe LLM Applications with Programmable Rails |
| **Authors** | Rebedea, T., Dinu, R., et al. |
| **Year** | 2023 |
| **Venue** | NVIDIA (toolkit paper) |
| **URL / DOI** | https://www.semanticscholar.org/paper/NeMo-Guardrails |
| **Method** | Introduces Colang, a domain-specific language for defining programmable guardrail policies that intercept/validate input and output across five pipeline stages |
| **Dataset** | N/A (framework) |
| **Key result** | GPU-accelerated architecture achieves sub-100ms response times; native integration with LangChain/LangGraph |
| **Limitation** | General-purpose conversational control; does not enforce provenance-aware authority ordering between system instructions and untrusted content unless explicitly configured |
| **Relevance** | Evaluated directly in Week 2 as a candidate input-guardrail framework; its LLM-based Colang intent classification proved unreliable on a local 7B model for this project's injection-detection task, motivating the switch to a deterministic Python guardrail (documented as RQ5 in the proposal) |

**Notes:**
> Limitation noted here matters a lot for SOC use case — by default it won't distinguish "trusted system prompt" from "untrusted log content" without explicit configuration. See Paper 7 (Instruction Hierarchy) for a primary paper addressing exactly this gap.

### Paper 5 — Presidio

| Field | Content |
|---|---|
| **Full title** | Presidio: An open-source framework for detecting, redacting, masking, and anonymizing sensitive data (PII) |
| **Authors** | Microsoft |
| **Year** | Ongoing (actively maintained) |
| **Venue** | GitHub / Microsoft open source |
| **URL / DOI** | https://github.com/microsoft/presidio |

### Paper 6 — FActScore

| Field | Content |
|---|---|
| **Full title** | FActScore: Fine-grained Atomic Evaluation of Factual Precision in Long Form Text Generation |
| **Authors** | Min, S., Krishna, K., Lyu, X., Lewis, M., Yih, W., Koh, P.W., Iyyer, M., Zettlemoyer, L., Hajishirzi, H. |
| **Year** | 2023 |
| **Venue** | EMNLP 2023 |
| **URL / DOI** | https://arxiv.org/abs/2305.14251 |
| **Method** | Breaks a long-form generation into individual "atomic facts," then checks each one against a reliable knowledge source, reporting the percentage supported |
| **Dataset** | Human-written biographies generated by InstructGPT, ChatGPT, and PerplexityAI, with human factuality annotations; also an automated estimator validated against 6,500 generations from 13 LMs |
| **Key result** | Even strong commercial models are far from perfectly factual (ChatGPT: 58% atomic-fact precision on biographies); the automated FActScore estimator matches human judgment with under 2% error |
| **Limitation** | Designed for open-domain biographical text with a broad reference corpus (Wikipedia); doesn't address a domain where the "knowledge source" is a structured, versioned technical database (like NVD or MITRE ATT&CK) rather than free-text biography articles |
| **Relevance** | This project's core method — decompose an LLM report into claims (CVE IDs, ATT&CK technique IDs), verify each atomically against an authoritative source, classify by outcome — is structurally the same pattern FActScore establishes, specialized to the security domain. Good citation for justifying the methodology, not just the SOC application |

**Notes:**
> This is the strongest "prior art for our core method" citation in the whole review — worth citing prominently in the methodology section, not just related work, since the four-class taxonomy (FABRICATED/REAL_BUT_IRRELEVANT/REAL_AND_PLAUSIBLE/UNVERIFIED) is a domain-specialized descendant of this atomic-verification idea.

### Paper 7 — The Instruction Hierarchy

| Field | Content |
|---|---|
| **Full title** | The Instruction Hierarchy: Training LLMs to Prioritize Privileged Instructions |
| **Authors** | Wallace, E., Xiao, K., Leike, R., Weng, L., Heidecke, J., Beutel, A. |
| **Year** | 2024 |
| **Venue** | arXiv (OpenAI) |
| **URL / DOI** | https://arxiv.org/abs/2404.13208 |
| **Method** | Proposes an explicit instruction hierarchy (system prompt > trusted user input > untrusted third-party content) and an automated synthetic-data generation method to fine-tune models to selectively ignore lower-privileged instructions when they conflict with higher-privileged ones |
| **Dataset** | Synthetically generated conflicting-instruction examples; evaluated against held-out prompt injection and jailbreak attack types not seen during training |
| **Key result** | Substantially increases robustness against injection/jailbreak attacks, including attack types absent from training data, with minimal loss of general capability |
| **Limitation** | Requires fine-tuning access to the base model — not applicable as a drop-in guardrail for a third-party API model (like this project's Groq-hosted Llama backend), where the defense has to live in the input/output layer instead |
| **Relevance** | Fills the gap left by the InjecAgent paper (attack-side only) — this is a primary paper on the *defense* side, and it names precisely the property NeMo Guardrails' own documentation admits it lacks by default (see Paper 4's limitation): provenance-aware authority ordering between trusted and untrusted content |

**Notes:**
> Good paragraph pairing: cite Paper 4's limitation, then this paper as "here is what a principled fix to that gap looks like at the model-training level, versus this project's guardrail-layer approach at inference time."

### Paper 8 — Judging LLM-as-a-Judge

| Field | Content |
|---|---|
| **Full title** | Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena |
| **Authors** | Zheng, L., Chiang, W., Sheng, Y., Zhuang, S., Wu, Z., Zhuang, Y., Lin, Z., Li, Z., Li, D., Xing, E.P., Zhang, H., Gonzalez, J.E., Stoica, I. |
| **Year** | 2023 |
| **Venue** | NeurIPS 2023, Datasets and Benchmarks Track |
| **URL / DOI** | https://arxiv.org/abs/2306.05685 |
| **Method** | Uses strong LLMs (e.g. GPT-4) as automated judges to score model responses to open-ended questions, then validates judge reliability against large-scale human preference data (MT-Bench, Chatbot Arena) |
| **Dataset** | MT-Bench (multi-turn question set), 3K expert votes, 30K human-preference conversations from Chatbot Arena |
| **Key result** | Strong LLM judges achieve over 80% agreement with human preferences — comparable to human-human agreement — but exhibit documented biases: position bias, verbosity bias, self-enhancement bias, and limited reasoning ability on math/logic questions |
| **Limitation** | Validated on general open-ended chat quality, not on a security-specific, high-stakes factual-verification task like classifying whether a CVE/ATT&CK citation is grounded — the documented biases (especially self-enhancement, if the same model family judges and generates) are a real risk to control for |
| **Relevance** | Direct methodology source for the planned LLM-judge baseline (Aug 23 milestone) — its documented bias list is exactly what to check for/report when using an LLM judge as a comparison point against this project's deterministic, database-grounded verification |

**Notes:**
> When implementing the LLM-judge baseline, deliberately use a different model family for the judge than for the SOC agent's own analysis, to avoid the self-enhancement bias this paper documents.
